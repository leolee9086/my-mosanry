# 布局引擎文件夹结构优化 - 2025-06-29

今天对昨天重构的布局引擎代码进行了进一步的组织优化，将不同的布局引擎放到了各自的子文件夹中。这次改进主要是关于代码组织结构，而不是功能或性能的变化。

## 之前的结构

昨天的重构已经将大文件拆分成了多个小文件，但是所有文件都平铺在同一个目录下：

```
layout-engines/
├── types.ts
├── layoutUtils.ts
├── useMasonryLayout.ts
├── useGridLayout.ts
├── useJustifiedLayout.ts
├── masonry-utils.ts
├── grid-utils.ts
└── justified-utils.ts
```

这种结构在文件数量较少时还可以接受，但随着功能的增加，目录会变得越来越混乱。

## 新的文件夹结构

今天我按照功能将不同的布局引擎放到了各自的子文件夹中：

```
layout-engines/
├── index.ts               # 统一导出所有布局引擎
├── types.ts               # 共享类型定义
├── layoutUtils.ts         # 共享工具函数
├── masonry/               # 瀑布流布局
│   ├── index.ts           # 瀑布流布局入口
│   ├── useMasonryLayout.ts # 瀑布流组合式API
│   └── masonry-utils.ts   # 瀑布流纯函数
├── grid/                  # 网格布局
│   ├── index.ts           # 网格布局入口
│   ├── useGridLayout.ts   # 网格布局组合式API
│   └── grid-utils.ts      # 网格布局纯函数
└── justified/             # 对齐布局
    ├── index.ts           # 对齐布局入口
    ├── useJustifiedLayout.ts # 对齐布局组合式API
    └── justified-utils.ts # 对齐布局纯函数
```

## 优点与收获

这次重组有几个明显的优点：

1. **关注点分离**：每种布局模式的代码都在自己的文件夹中，更加内聚
2. **更好的可扩展性**：如果要添加新的布局模式，只需创建一个新的文件夹
3. **命名空间隔离**：可以使用相同的函数名，如每种布局都有自己的`appendItems`
4. **更清晰的导入路径**：使用命名空间式导入，如`import * as MasonryLayout from './masonry'`
5. **统一的入口点**：通过`index.ts`统一导出所有布局引擎，使用更加灵活

## 遇到的问题

在迁移过程中遇到了一些小问题：

1. **导入路径更新**：需要修改所有文件中的相对导入路径，如`../types`而不是`./types`
2. **循环依赖风险**：需要注意避免文件之间的循环依赖
3. **类型声明位置**：考虑是将类型放在各自的文件夹中，还是放在共享的`types.ts`中

## 思考与启发

这次重构让我对代码组织有了新的思考：

1. **按功能组织 vs 按类型组织**：
   - 按功能组织（如我们现在做的）让相关代码更加内聚，更容易理解整体功能
   - 按类型组织（如MVC模式）可能在某些项目中更合适

2. **文件夹深度的权衡**：
   - 文件夹层级太浅，会导致单个目录文件过多
   - 文件夹层级太深，会导致导入路径复杂
   - 需要找到平衡点，我认为2-3层是比较理想的

3. **入口文件的重要性**：
   - 每个模块都应该有一个明确的入口文件（如`index.ts`）
   - 入口文件应该只导出该模块的公共API，隐藏内部实现细节

## 下一步计划

1. 考虑为每种布局引擎添加单元测试
2. 可能会探索将计算密集型操作移至Web Worker
3. 考虑添加更多的布局模式，如瀑布流+对齐的混合模式

总的来说，良好的代码组织结构对于大型项目至关重要，它不仅提高了可维护性，也让新功能的添加变得更加容易。
